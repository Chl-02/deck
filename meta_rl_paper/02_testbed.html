테스트베드 — 플랜트, EMS, 9-knob 권한, capture 지표

이 장은 논문의 §2(테스트베드)와 §3(평가 프레임)에 들어갈 재료의 전체 그림이다. 무엇을 시뮬레이션하고, 누가 무엇을 결정할 권한을 갖고, 성능을 어떤 자로 재는지 — 이 세 가지를 정확히 이해해야 4장의 결과가 읽힌다.

2.1플랜트 — backward-facing power-domain HEV

시뮬레이션 대상은 실차 ECU의 복제가 아니라 backward-facing, power-domain으로 단순화한 HEV 테스트베드다(models/modified/HEV_MetaEMS_Model.slx, scripts/setup_project.m이 Simulink API로 생성). 요구 파워 P_dem을 엔진/모터 파워로 나누어 SOC와 연료를 적분한다. 토크·변속기·클러치 동역학은 풀지 않는다.

구성값출처

알려진 단순화 (논문 §8 Limitations의 재료): 무손실 배터리(ideal energy reservoir — 왕복효율 0.97 파라미터는 존재하나 미사용), 시동 페널티 2.0 g/start(공회전 등가시간 K≈20.5 s — 재래식 실측의 2.2배 상단값), 저속 모터 파워캡 미모델링(단, 검증 결과 비활성: V6 트레이스 100,800스텝 + SUMO 스파이크 2.25M스텝에서 binding 0건, v_base=9.53 m/s는 Toyota WEVJ 1차 출처로 확정), 냉시동 농후화 미모델링, 파워 상승 동특성 생략.

플랜트 신뢰성 앵커 (2026-07-27 신규)

EPA 표준 사이클 절대 연비: UDDS 3.87 / HWFET 3.52 L/100km — 실차 4세대 Prius(약 4~5)와 정합. SUMO 장기 프로파일의 9~10.5 L/100km는 플랜트 결함이 아니라 정차 지배 프로파일 특유(정차 46%, 그중 33%는 min-on timer로 엔진 ON)임이 확인됐다. 논문 §2에 인용, 절대 연비의 외부 비교는 여전히 금지.

2.2production-like map/rule EMS

제어기는 양산 EMS를 닮은 map/rule 구조다. 네 가지 모드(EV / HEV / Charge / Regen)를 오가며 다음을 결정한다:

  • 엔진 on/off — 2-D lookup P_eng_on_th = f(속도, SOC) (ECMS 유도 smoothed reference map) + hysteresis(기본 4 kW) + min-on/off timer (60 s / 10 s — 이 timer가 나중에 정차 idle 문제 #21의 원인이 된다).
  • power split — HEV 모드에서 P_eng = P_dem + K_charge·SOC부족 − K_discharge·SOC잉여, 모터가 나머지를 담당.
  • SOC 관리 — 기준 SOC 0.55(적응 범위 [0.45, 0.65]), 0.40 이하면 Charge 모드, SOC 의존 배터리 충·방전 한계 taper.
  • adaptive base — SOC 부족·최근 부하로 engine-on 문턱과 SOC 기준을 즉시 조정하는 강한 물리 휴리스틱(무감쇠 적용). 학습 어댑터가 이기려면 넘어야 했던 첫 상대이자, capture 분모의 기준선(adaptive_rule_calibration)이다.

모든 arm이 같은 9-knob 권한과 같은 관측을 갖는다. 이 "권한 동등"이 이 논문의 방법론적 자산이다. 차이는 오직 누가 knob 값을 정하는가뿐이다.

2.5V6 구조와 confidence gate

최종 학습 head V6 = residual-on-fitted-base:

final knobs = fitted rule 출력 (base) + gate( policy residual, 정규화 ±0.3 )
confidence가 0이면 fitted rule로 정확히 복귀한다. pretrain 없이 fitted base 자체가 구조적 warm-start가 되어, V3를 괴롭힌 seed 분산(실패 seed, 50pt 범위)을 해결했다 (V4·V5는 teacher pretrain으로 분산은 잡았으나 평균이 하락했었다 — V6는 둘을 동시 해결).

confidence gate는 세 신호의 최솟값이다 — distribution(학습 분포 대비 관측 z-score envelope), safety-margin(SOC/배터리 한계 근접 시 방향별 억제 — 예: 저SOC이면 engine-on을 늦추는 방향만 차단), stability(포화·부호 반전· action rate). 평균 성능 장치가 아니라 OOD에서 개입량을 줄이는 배포 안전장치다 (OOD capture: gated 23.7 vs ungated 7.5, 조건 단위). 알고리즘 자체는 PEARL-style 확률적 context encoder + SAC — 새 알고리즘 제안이 아니라 표준 구성의 제한적 적용으로 포지셔닝한다.

2.6capture 지표 — 논문에서 가장 중요한 정의

  • 분모의 성격 — oracle은 에피소드를 다 보고 나서 knob을 고르는 사후 튜너다. 같은 9-knob 권한 안에서 도달 가능하지만, 배포 제어기는 주행 중에 결정해야 하므로 격차 일부는 정의상 제어 기회가 아니다. 그리고 4장의 발견: 남은 격차는 태스크의 함수가 아니라 개별 실현에 붙어 있다.
  • 지표 — SOC_tail_risk (SOC 오차 밴드 기반: warning 0.03~0.06, critical 0.06~0.10). 연료·스위칭·SOC보정연료는 guardrail.
  • 집계 규약 — 논문은 케이스 단위 pooling(120 에피소드, 1건=1표)으로 통일하고 조건 단위(21 condition)는 각주. 단일 split 축에서는 둘이 수학적으로 일치.
  • 무결성 assert — Phase A 120케이스의 분모 Σ(adaptive−oracle) = 5.6296. 이 값이 아니면 config 오염(--v3-config 함정, 실제 2회 발생). scripts/report_paper_tables.py에 assert 내장.

2.7데이터와 태스크 설계

  • 주행 프로파일 4계열 — EPA 표준 사이클(전부 heldout 앵커) · NREL DriveCAT(vocation 단위 holdout) · NGSIM(실주행 micro-profile 보조) · SUMO 생성(주력, targeted additions 포함). meta-RL 학습에 5,187 프로필.
  • 태스크 축 — task = 주행 세그먼트 + 느린 운전 조건(profile + initial_SOC + road_grade + mass_scale). 은닉 축 3종(accessory_load 1.05→4.0 kW, battery_derating 1.0→0.7, friction 1.0→0.6)은 물리에는 연결되지만 관측·컨텍스트·confidence feature에서 의도적으로 격리 — rule과 encoder 모두 구조적으로 못 보므로 공정 비교가 성립하고, 나중에 정보 축 실험(T0h)에서 "정답을 주면 오르는가"를 시험하는 반사실이 된다.
  • weather — V5에서 학습 통합(wet/heavy_rain/snow 학습, friction_mu 0.65/0.5/0.35), ice(0.2)는 held-out 외삽 시험.
  • 누수 0 — 학습/평가 프로필 교집합 0 (fitted·meta-RL 양쪽, 두 키 모두), 하이퍼파라미터 선택도 train 전용. 은닉 축 외삽값은 양쪽 arm에 동일하게 OOD.
  • 정보 티어 T0~T2b — 관측 특징 사다리(10→22개). 각 arm은 기준 T0(10특징)의 상위집합이라, T0 대비 capture 차이가 곧 해당 추가 특징의 가치다. T0h(14개)가 결정적: 은닉 태스크 축 4개의 정확한 값을 추가한 반사실 arm.
